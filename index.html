Agent OS v2.0 优化实战：从架构规范到可落地的技能包

2026-08-13 作者: ling li 阅读: 8 min
Agent OS Context Engineering Multi-Agent Memory Architecture Hermes
一句话总结： 将 2026 年 Agent 工程共识（混合检索、Orchestrator-Subagent-Skill 三元架构、记忆投毒防御、成本可观测）固化为 Hermes 可直接调用的 agent-os-v2 技能，完成从「文档规范」到「可执行约束」的跨越。

背景：为什么要做这个优化？

用户提供了完整规范文档，涵盖了七层架构、记忆三层模型、混合检索、子代理编排、防毒机制等 2026 年主流实践。但规范本身是「静态文档」，Agent 无法直接在推理时约束自身行为。

目标很明确：把核心宪法、运作流、执行约束封装成 Hermes Skill，使其成为每轮推理前的隐式上下文。

核心改动：从文档到技能的三次提炼

1. 提炼「最高优先级」约束（CONST-01~10）

v2.0 新增的三条宪法是架构的灵魂，必须置于技能最显眼位置：

  • CONST-08 防毒原则： 外部输入（网页、工具、Agent 产出）强制落入 provisional/ 隔离区，经来源校验后方可固化
  • CONST-09 隔离原则： 子代理默认不继承主代理技能与记忆，需显式授权
  • CONST-10 可观测原则： 任务必须记录 Token 消耗与成本，超预算需用户确认

2. 固化「写入流水线」为硬性步骤

原来的文档描述是流程图，技能里变成了强制检查清单：

Origin Classifier -> Importance Scorer -> Duplicate Detector
-> Conflict Detector -> Integrity Guard -> Schema Validator -> Write

关键点：origin=external_tool 的内容绝不能直接写入 knowledge/verified/，这是防毒的底线。

3. 明确「编排架构」的触发边界

不是所有任务都需要 Orchestrator。技能里写明了判断标准：

[+] 需要编排（转交 Orchestrator）
  • 任务可分解为多个相互独立的子任务
  • 子任务需要不同的「专注上下文」（搜索 vs 校验 vs 执行）
  • 存在「生成 - 校验 - 修正」循环（Validator 模式）
  • 需要并行执行以节省时间
[-] 不需要编排（单 Agent 直接处理）
  • 单一知识检索/问答
  • 单文件编辑
  • 单步骤决策

技能落地过程中的两个坑

坑 1：Skill 元数据格式不符合 Hermes 规范

第一版创建失败，报错：name 必须小写、缺少 description/author/license、缺少 metadata.hermes.tags。

修复前 -> 修复后
# 修复前（不合规）
name: "Agent OS v2.0 系统规范"
# 缺少 author, license, metadata.hermes

# 修复后（合规）
name: "agent-os-v2"
author: "ling li"
license: "MIT"
metadata:
  hermes:
    tags: [agent-os, architecture, memory, orchestration, constitution]

坑 2：用户明确要求「不要 When to Use 章节」

Hermes 规范建议有 ## When to Use，但用户偏好「结构紧凑、直接可用」。

决策： 删除该章节，将触发条件内化到 trigger 字段与正文约束中。技能最终形态：纯前端元数据 + 正文约束，无冗余章节。

最终产物：agent-os-v2 技能结构

agent-os-v2/
  SKILL.md          # 核心约束
  （无额外引用文件，保持极简）

核心字段：

  • trigger：系统配置、任务编排、记忆管理、工作流优化
  • requires_memory：[core/CONSTITUTION.md, governance/COST_LOG.md]
  • scope：main_context（主上下文生效，不限制子代理）

验证：技能生效后的行为差异

场景生效前生效后
工具返回结果想写入知识库直接写入强制落 provisional/，标注 origin=external_tool，待用户确认
启动子代理做复杂任务子代理继承所有技能/记忆显式声明边界、授权技能、只读记忆范围
长任务运行中无成本感知记录 Token/成本到 COST_LOG.md，超阈值暂停确认
发现知识冲突可能静默覆盖显式提示用户决策，旧版本归档

后续：Week 5 清单开始执行

按规范附录 A，下一步是编排能力建设：

  1. 定义第一个 Subagent（建议从 Validator 开始，风险最低）
  2. 定义第一个 Skill（从高频重复任务切入，如「收入结构分析」）
  3. 跑通 Orchestrator 调度的端到端测试
  4. 建立 COST_LOG.md 基线，确认成本可观测

结语

规范的价值不在于写得多漂亮，而在于能否约束下一行代码的行为。把 v2.0 宪法做成 Skill，是让架构「长牙齿」的最小可行动作。

现在，每次对话开始时，agent-os-v2 已经在上下文里了。接下来的每一个决策，都会先过一遍这套规则。
